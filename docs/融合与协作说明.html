一个接收器，两种展示

本人只读账号↓一个结构化接收器
未读确认 · 去重 · 规则↓灵动岛列表 ＋ 可关闭桌面弹幕

在未来的融合进程中，只让一份接收器运行。灵动岛直接消费结构化消息；弹幕通过小型转换层把同一条消息交给现有透明 Overlay。这样既保留会话身份和提醒规则，也能复用你已经做好的短消息移动、长消息分页和队列上限。

“静音提醒”仍继续收消息；“暂停弹幕”只暂停展示；“停止接收”关闭获取并清空待展示内容。三种操作要明确分开，不能让两套设置互相覆盖。

本机读取和服务器读取是两种不同的数据处理方式。暂时不把本机 profile、消息或授权搬上服务器，也不把服务器凭据交给灵动岛。是否以后共用云端入口，需要单独决定。

第一轮只做三件事

  1. 统一账号入口与接收事件。在同事版基础上参数化 CLI 路径与 profile，保留结构化身份和未知未读重试；不要修改用户全局 CLI。
  2. 接上透明弹幕。同一个接收结果进入灵动岛和可选弹幕通道；测试同条消息只入队一次、短消息移动、长消息全文分页、停止后不再展示。默认关闭新弹幕通道，避免一安装就打断工作。
  3. 补齐本机设置与演示。用一个本机设置页控制弹幕开关、暂停和外观。先用合成消息演示，再安排本人授权的真实消息验收。外观 Agent 白名单与核心功能边界继续保留。

这里写的是下一轮工作顺序，不是已经完成的产品功能。双方现有实现和原始导入哈希都保留下来，方便比较和回退。

你们不需要手写 Git 命令

你们负责说清需求、看实际效果、做产品决定；Agent 负责建分支、写代码、跑检查和开 PR。PR 可以理解为“这一轮改动的待合入版本”，合入 main 后才成为共同基线。

谁建议负责什么
你消息接收、授权、弹幕规则及正式发布的最终确认
同事灵动岛外壳、交互和本机设置界面；涉及核心时与你共同确认
各自的 Agent在各自账号、独立分支或 worktree 中实现和测试，不直接覆盖 main

每项需求在 GitHub Issues 写清“现在怎样、希望怎样、怎样算完成”。两个 Agent 不同时修改同一工作目录；若任务涉及同一个核心文件，先约定由一个 Agent 集成，另一边做审阅。

同事使用自己的 GitHub 和飞书账号。仓库写入权限不等于服务器发布权限，也不等于有权读取你的消息。普通用户的外观 Agent 只调用外观 MCP；团队拿到源码后技术上能改源码，核心边界仍需要评审和发布权限约束。

仓库先设为私有，保留双方来源与第三方许可。当前账号的私有仓库强制分支保护请求被 GitHub 套餐限制拒绝；未升级、未公开。现在只能靠 PR 流程约定，CODEOWNERS 文件本身不阻止直接推送。GitHub 官方保护说明。
